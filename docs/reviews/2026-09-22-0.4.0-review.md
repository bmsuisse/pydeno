# Code review: pydeno 0.4.0 (`a51a0a4..66cfa57`)

Reviewed after 0.4.0 was published, so this is an input to 0.4.1, not a ship
gate. Fixes that were safe to land are on `review/0.4.1-followups`; everything
else is recorded here because acting on it changes behaviour.

Verification on this branch, macOS arm64: `cargo fmt --all -- --check` clean,
`cargo clippy --tests -- -D warnings` clean, `ruff check` + `ruff format
--check` clean, `pytest tests/` **553 passed / 0 skipped** in both the
`release` and the `unoptimized + debuginfo` profile.

## Fixed on this branch

### F1. Lost-wakeup hang in `Watchdog::drop` (`src/runtime/runner.rs:338`)

`WatchdogState.shutdown` sits behind its own mutex, but the watchdog thread
reads it while holding `armed` — the mutex `wake` is paired with — and only
releases `armed` atomically as it enters `Condvar::wait`. `drop` set the flag
and signalled without taking `armed`, so the notification could land after the
watchdog had read `shutdown == false` but before it was parked. Condvar
notifications are not queued, so it was dropped; with nothing armed the thread
parked on the unbounded `wait` arm forever and `join()` never returned —
closing a runtime could hang. Fixed by holding `armed` across the flag write,
in the same lock order the watchdog thread uses.

Narrow window, never observed, but it is the exact "runtime dropped while
armed" race the rewrite had to get right.

### F2. `STACK_HEADROOM_BYTES` comment was wrong (`src/runtime/js_value.rs:69`)

It claimed 640 KiB "trips this check at depth 22 in *both* profiles".
Re-measured by bisecting the first rejected depth of the same `{n: {n: ...}}`
chain: **22 in debug, 743 in release**. Corrected, and the consequence the old
comment left implicit is now stated — see O1.

### F3. `SnapshotBuilder` is unsandboxed and said so nowhere

`snapshot.rs::create_runtime` builds a bare `JsRuntimeForSnapshot` with **no**
`python_extension`, so the bridge bootstrap that deletes `Deno`/`__bootstrap`
never runs there. Confirmed: `Deno.core.ops.op_print('MARKER', false)` from a
`SnapshotBuilder.execute_script` script writes straight to the host's stdout.
That is by design — snapshot input is host code — but neither the `.pyi` nor
the Rust type said so. Documented on both, including the reassurance that the
resulting snapshot *is* safe to hand to `Runtime` (the bridge deletes those
globals out of the restored heap; pinned by `tests/test_guest_globals.py`).

### F4. No CHANGELOG

0.4.0 removed `IsolatePool`/`PooledIsolate`, deleted `__bootstrap`/`__infra`,
and turned a runaway microtask queue from "returns a value" into "raises" —
none of it written down anywhere a user upgrading from 0.3.x would look.
Added `CHANGELOG.md`.

## Open — needs a deliberate 0.4.1 decision

### O1. The stack-headroom check is unconditional, and debug can't reach the default depth limit

`LimitTracker::enter` runs the headroom check on every call, not only when
`max_serialization_depth` has been raised. Measured on this checkout:

| profile | first rejected depth | that profile's real crash boundary |
|---|---|---|
| `unoptimized + debuginfo` | 22 | ~40 |
| `release` | 743 | ~1100–1200 |

So in a debug build, **any** value nested deeper than 21 is rejected
regardless of `max_serialization_depth`, and the default limit of 100 is
unreachable. Published wheels are release builds, so users are unaffected; it
is developers and the debug CI job who see it. No test covers default-config
nesting between 22 and 99, which is why the suite is green either way.

Options: leave it and document (done), or make the budget profile-aware
(`#[cfg(debug_assertions)]`), or raise the OS-thread/V8 stack so debug frames
fit. All change behaviour; none is a 0.4.0 patch.

Second-order: the budget is measured from the *thread* anchor, not from the
serializer's entry frame, so frames already on the stack count against it. A
conversion from inside a host-op callback has slightly less headroom than the
same conversion from a top-level `eval`. Conservative in the safe direction,
but it means the effective depth limit is context-dependent.

### O2. Timeout cross-talk between concurrently armed deadlines

The watchdog tracks a set of deadlines but the isolate is single-threaded, so
a fired deadline calls `terminate_execution()` once and kills *whatever is
currently running*, which need not be the job that timed out. A sync `Eval`
dispatched inline while an async job is parked on a short-timeout promise will
be terminated by that async job's deadline; its own `apply_watchdog_result`
sees its token un-fired and reports a bare termination error instead of a
timeout. Pre-existing — the spawn-per-call watchdog behaved identically — but
the rewrite is the moment to decide whether deadlines should be attributed.

Related, cosmetic: `ensure_reason` picks the last fired entry via
`.rev().find()`, and `swap_remove` in `disarm` makes `armed`'s order
arbitrary, so the reason attached to a multi-expiry pass is effectively
arbitrary too.

### O3. `RuntimeError::Timeout` is indistinguishable from any other failure

It maps to `PyRuntimeError` (`src/runtime/python/error.rs:57`), so a caller
can only tell a timeout from an internal error by matching `"timed out"` in
the message — and the repo's own tests do exactly that
(`tests/test_microtask_timeout.py`). A dedicated `pydeno.TimeoutError`
(subclassing `RuntimeError` for compatibility) would be a clean 0.4.1 addition.

### O4. `CLAUDE.md` documents a streaming API that does not exist

The "Streaming between JavaScript and Python" example uses
`rt.create_js_stream_from_python(...)` and `__pydeno_get_stream__(id)`.
Neither symbol exists anywhere in `src/`, `python/` or `tests/` — the only hit
for `__pydeno_get_stream__` in the whole tree is that example. Pre-existing
rot that the rename carried forward (it renamed a symbol that isn't real).
Fixing it needs the actual stream API, so it is flagged rather than guessed at.

## Checked and clean

- **Guest-global allowlist.** `Reflect.ownKeys(globalThis)` is 76 keys and is
  a subset of the pin. `Deno`, `__bootstrap` and `__infra` are all `undefined`
  on a fresh runtime, under `RuntimeConfig(snapshot=)`, and after failed
  dynamic imports. The lazy-init path the brief worried about is real —
  deno_core 0.409's `01_core.js:956` documents that `op_load_ext_script`
  temporarily reinstalls a snapshot-time `__bootstrap` — but it is
  unreachable: pydeno registers no `lazy_loaded_js`, and `PythonModuleLoader`
  denies every specifier it does not know, so guest `import("ext:core/mod.js")`,
  `import("ext:core/ops")` and `import("node:fs")` are all refused at resolve
  time. `RuntimeConfig(bootstrap_script=)` runs *after* the bridge, so it
  cannot resurrect anything either. No third way in was found.
- `Atomics.wait` on a `SharedArrayBuffer` (both in the allowlist) is
  interrupted correctly by `terminate_execution` — a 30 s wait under a 1 s
  timeout raised at 1.01 s rather than wedging the runtime thread.
- Watchdog `generation`/staleness: ids are monotonic `u64`, `disarm` matches
  by id, so a stale token can never resolve a newer deadline. Fired entries
  stay in the set with `fired: true` and are excluded from `next_deadline`, so
  there is no repeat fire and no busy loop. Tokens cannot leak: `cancel_all_jobs`
  finishes the active job and every pending one, and `respond` disarms.
- Cycle detection: the path-based `Vec<Local<Object>>` + `strict_equals` check
  is correct and strictly better than the identity-hash set it replaced.
- Rename: zero whole-word `peno` matches anywhere in the tree, zero
  `IsolatePool` references outside the disclaimed historical review record, no
  stale CI matrix entries, and `docs/stubs/pydeno/_pydeno.py` resolves.
- Zero references to any consuming project. MIT fork attribution is
  in `LICENSE` only (`docs/contributing/upstream-divergence.md` describes the
  fork but carries no licence grant). One oddity worth a decision, not a bug:
  `pyproject.toml` still lists the upstream author as the package `authors`
  entry with bmsuisse as `maintainers`.

## Resolution in 0.4.1

All four open items were decided. Two produced code changes, two produced
documentation plus the test coverage that would have caught them.

### O1 — decided: keep the check, fix the message and the docs

The premise that the check "shouldn't be the thing that rejects ordinary
data" does not survive measurement: in an `unoptimized + debuginfo` build,
nesting past ~31 genuinely cannot be serialized. Raising
`STACK_HEADROOM_BYTES` to 6 MiB (enough for depth 213 in debug) was tried and
reproduced the abort the check exists to prevent — `Check failed:
IsOnCentralStack()` from `Isolate::StackOverflow`, C stack trace running
straight through `value_to_js_value_internal`. The check is the only thing
between a debug build and that abort, so it stays at 640 KiB.

A per-profile budget cannot help either: debug needs ≥3 MB to reach depth 100
and release must stop short of ~984 KB, so no pair of constants both allows
the documented default and preserves the backstop.
`v8::CreateParams::set_stack_limit` does not move the boundary — verified:
`StackGuard::InitThread` overwrites it from `v8_flags.stack_size` when the
isolate is entered on a thread, so guest JS recursion stayed at 9983 frames
with the limit set. That flag is process-global and would also apply to
`SnapshotBuilder` isolates, which are created on whatever Python thread calls
them, possibly a 512 KB one.

What changed: the rejection now names the build profile as the cause instead
of reading as a fault in the caller's data, `RuntimeConfig.max_serialization_depth`
documents the ceiling, and `tests/test_serialization_headroom.py` covers
depths 22/40/60/99 at the default configuration — the band nothing exercised,
which is why this was not caught.

Closing the gap properly means shrinking the debug frame:
`value_to_js_value_internal` is one large function whose every branch gets its
own stack slots unoptimized, at ~29.5 KB a frame against ~0.9 KB optimized.
That is a refactor, not a patch.

### O2 — decided: not fixable cleanly, documented and pinned

Reproduced exactly as described: an async job parked on a never-resolving
promise under a 0.3 s timeout, with an untimed sync `Eval` dispatched inline,
ends with the async job reporting its timeout correctly and the *sync* call
failing with a bare `Error: execution terminated`.

It is a property of one isolate on one thread, not a bug in the deadline set.
`terminate_execution` is isolate-wide and has no per-job scope; attributing
deadlines would mean either declining to fire while an unrelated job is inline
(defeating the deadline exactly when the wedged job *is* the inline one) or
tracking isolate ownership at every instant, which is the model with extra
steps. Documented on `ArmedDeadline` and `RuntimeConfig.timeout`, pinned by
`tests/test_timeout_cross_talk.py`.

The cosmetic half *was* fixed: `ensure_reason` now takes the deadline that
expired first rather than the last entry in a `Vec` whose order `swap_remove`
makes meaningless.

**Found while pinning it, and left open:** `PendingJob::expired` calls
`terminate_execution()` and nothing ever calls `cancel_terminate_execution()`
for it — only the synchronous path does, in `resolve_sync_watchdog`. So an
async job that times out on a pending promise leaves the isolate latched in
termination and *every* later call on that runtime fails with `execution
terminated`, with nothing else in flight. Confirmed pre-existing by reverting
0.4.1's `runner.rs` changes. This is a worse defect than O2 itself and is
outside what 0.4.1 was scoped to; it is pinned as found by
`test_runtime_is_unusable_after_an_async_deadline_fires`, which whoever fixes
it should delete and replace with an assertion of reuse.

### O3 — done: `pydeno.RuntimeTimeout`

Added, subclassing `RuntimeError` so every existing `except RuntimeError`
keeps working. Named `RuntimeTimeout`, not `TimeoutError`, because Python's
builtin of that name derives from `OSError`. `tests/test_timeout_exception_type.py`
asserts both the new type and the compatibility guarantee.

### O4 — done: the docs were wrong, not the code

`git log -S` confirms `create_js_stream_from_python` and
`__pydeno_get_stream__` only ever existed in `CLAUDE.md`, from the initial
commit. The example now uses the real API,
`rt.stream_from_async_iterable(...)`, and is executed rather than merely read
by `tests/test_claude_md_api_references.py`, which also checks every
`Runtime` attribute and guest global the file names.
